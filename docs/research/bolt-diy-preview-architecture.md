# How bolt.diy runs application previews

Date: 2026-08-15

Repository revision inspected: [`stackblitz-labs/bolt.diy@2e254ac`](https://github.com/stackblitz-labs/bolt.diy/tree/2e254ac19a696394030601bc602f54945b12bfc4)

## Executive conclusion

bolt.diy does **not** create a Docker container for each generated application's preview. Its generated Node.js project, filesystem, shell, package manager, and dev server run inside a StackBlitz **WebContainer in the user's browser tab**. The URL emitted by that browser-side dev server is placed directly in a sandboxed iframe.

The Docker support advertised by bolt.diy is a way to run the bolt.diy host application itself; it is not the preview runtime. This distinction explains the perceived speed: bolt.diy removes server-side resource provisioning, image/volume creation, and preview-proxy setup from the preview critical path. It does not make `npm install` free; dependency installation and the framework dev server still run, but on the user's machine inside the WebContainer.

For Horizon, the strongest design is a **hybrid**: use a WebContainer as an immediate, non-authoritative UI/Node draft preview while the governed per-project Docker workspace starts in parallel. Keep Docker as the authoritative environment for databases, protected secrets, arbitrary/native tooling, validation, publishing, and multi-user continuity.

## Runtime flow traced from source

```text
Browser loads creator workbench
  -> WebContainer.boot({ coep: "credentialless", workdirName, ... })
  -> generated/imported files are written into the browser-side filesystem
  -> /bin/jsh is spawned and connected to the xterm UI
  -> shell action runs npm install
  -> start action runs npm run dev (or start/preview)
  -> WebContainer emits port/server-ready with a preview URL
  -> preview store records { port, ready, baseUrl }
  -> React renders baseUrl in a sandboxed iframe
  -> dev-server HMR and explicit refresh messages update the preview
```

### 1. Boot happens in the browser, once per page

The WebContainer module is a no-op during SSR. On the client it calls `WebContainer.boot()` with `coep: 'credentialless'`, a configured working-directory name, and preview-error forwarding. During Vite HMR, the promise and loaded state are retained in `import.meta.hot.data`, avoiding a second boot. It also injects an inspector script and receives uncaught preview errors through `preview-message`.

Evidence: [`app/lib/webcontainer/index.ts#L17-L64`](https://github.com/stackblitz-labs/bolt.diy/blob/2e254ac19a696394030601bc602f54945b12bfc4/app/lib/webcontainer/index.ts#L17-L64).

This matches the official constraint that `WebContainer.boot()` may be called only once and only one WebContainer instance may be created per page.[^wc-quickstart]

### 2. bolt.diy writes files incrementally; it does not currently call `mount()`

Generated `<boltAction type="file">` actions are serialized by `ActionRunner`. Each action creates its parent directory and calls `webcontainer.fs.writeFile(...)`. Editor saves use the same WebContainer filesystem APIs. Project imports use WebContainer-backed filesystem adapters.

Evidence: [`app/lib/runtime/action-runner.ts#L120-L165`](https://github.com/stackblitz-labs/bolt.diy/blob/2e254ac19a696394030601bc602f54945b12bfc4/app/lib/runtime/action-runner.ts#L120-L165) and [`#L311-L339`](https://github.com/stackblitz-labs/bolt.diy/blob/2e254ac19a696394030601bc602f54945b12bfc4/app/lib/runtime/action-runner.ts#L311-L339).

There is no application-source call to `webcontainer.mount()` at the inspected revision. On restoration, bolt.diy reads a saved snapshot and replays `mkdir`/`writeFile` calls file by file: [`app/lib/persistence/useChatHistory.ts#L200-L256`](https://github.com/stackblitz-labs/bolt.diy/blob/2e254ac19a696394030601bc602f54945b12bfc4/app/lib/persistence/useChatHistory.ts#L200-L256).

The official API recommends `mount()` for instant bulk hydration and supports a binary snapshot generated by `@webcontainer/snapshot`.[^wc-quickstart][^wc-fs] Horizon should use bulk/binary mounting if it adopts this runtime rather than copying bolt.diy's file-by-file restoration path.

### 3. Install and dev-server commands are ordinary shell actions

For imported/restored Node projects, bolt.diy parses `package.json`, chooses `dev`, `start`, or `preview`, prepares a non-interactive `npm install`, and emits two actions:

- a blocking `shell` setup action;
- a non-blocking `start` action such as `npm run dev`.

Evidence: [`app/utils/projectCommands.ts#L41-L107`](https://github.com/stackblitz-labs/bolt.diy/blob/2e254ac19a696394030601bc602f54945b12bfc4/app/utils/projectCommands.ts#L41-L107) and [`#L110-L135`](https://github.com/stackblitz-labs/bolt.diy/blob/2e254ac19a696394030601bc602f54945b12bfc4/app/utils/projectCommands.ts#L110-L135). New projects use the same action protocol; the system prompt explicitly tells the model to emit `npm install` and `npm run dev` actions.

The workbench first spawns `/bin/jsh` in the WebContainer and wires its readable/writable streams to the terminal UI. Commands are typed into this long-lived shell and completion is detected from OSC control messages. Evidence: [`app/utils/shell.ts#L7-L89`](https://github.com/stackblitz-labs/bolt.diy/blob/2e254ac19a696394030601bc602f54945b12bfc4/app/utils/shell.ts#L7-L89) and [`#L116-L170`](https://github.com/stackblitz-labs/bolt.diy/blob/2e254ac19a696394030601bc602f54945b12bfc4/app/utils/shell.ts#L116-L170).

`ActionRunner` starts the dev-server command without blocking the remaining action queue forever and currently inserts a fixed two-second delay to avoid races. Evidence: [`app/lib/runtime/action-runner.ts#L188-L219`](https://github.com/stackblitz-labs/bolt.diy/blob/2e254ac19a696394030601bc602f54945b12bfc4/app/lib/runtime/action-runner.ts#L188-L219) and [`#L282-L309`](https://github.com/stackblitz-labs/bolt.diy/blob/2e254ac19a696394030601bc602f54945b12bfc4/app/lib/runtime/action-runner.ts#L282-L309).

The official WebContainer sequence is the same: spawn `npm install`, wait for its exit code, spawn the dev command, and wait for `server-ready`.[^wc-quickstart]

### 4. Preview discovery is event-driven

`PreviewsStore` subscribes to both:

- `server-ready`, used as the signal that a server accepts traffic;
- `port`, used to add, update, or remove preview entries and their URLs.

The store maintains `PreviewInfo { port, ready, baseUrl }` and handles multiple listening ports within the single WebContainer. Evidence: [`app/lib/stores/previews.ts#L169-L215`](https://github.com/stackblitz-labs/bolt.diy/blob/2e254ac19a696394030601bc602f54945b12bfc4/app/lib/stores/previews.ts#L169-L215).

The application therefore does not poll a health endpoint or wait for a server-side reverse proxy. StackBlitz's runtime gives it a routable URL when the in-browser server opens a port.

### 5. The preview URL is rendered directly in an iframe

The selected preview's `baseUrl` becomes React state and is passed to a sandboxed iframe. The UI can switch among ports, change paths, reload, resize into device frames, or open the preview in another tab/window.

Evidence: [`app/components/workbench/Preview.tsx#L93-L123`](https://github.com/stackblitz-labs/bolt.diy/blob/2e254ac19a696394030601bc602f54945b12bfc4/app/components/workbench/Preview.tsx#L93-L123) and [`#L981-L1005`](https://github.com/stackblitz-labs/bolt.diy/blob/2e254ac19a696394030601bc602f54945b12bfc4/app/components/workbench/Preview.tsx#L981-L1005).

For a standalone window, bolt.diy extracts the preview ID, reconstructs `https://<id>.local-credentialless.webcontainer-api.io`, embeds it in another iframe, and uses `BroadcastChannel` to request reloads on file-change messages: [`app/routes/webcontainer.preview.$id.tsx#L17-L96`](https://github.com/stackblitz-labs/bolt.diy/blob/2e254ac19a696394030601bc602f54945b12bfc4/app/routes/webcontainer.preview.$id.tsx#L17-L96). Inside the main preview, framework HMR can update the page through the already-running dev server; explicit saves can additionally broadcast refresh events.

### 6. Terminal and persistence are browser-local

The integrated terminal is not SSH and is not attached to a cloud VM. It is an xterm-style UI connected to the `/bin/jsh` WebContainer process streams.

Chat history and project snapshots are stored in browser IndexedDB database `boltHistory`, with separate `chats` and `snapshots` object stores. Evidence: [`app/lib/persistence/db.ts#L14-L51`](https://github.com/stackblitz-labs/bolt.diy/blob/2e254ac19a696394030601bc602f54945b12bfc4/app/lib/persistence/db.ts#L14-L51). On reload, source files are restored and setup/start actions are regenerated. The running process and memory are not a durable server session.

Git import/export and ZIP download provide additional portability, but browser-local IndexedDB is still the default snapshot store, not a multi-user source of truth.

## Boundaries and limitations

| Area | bolt.diy / WebContainer behavior | Horizon implication |
| --- | --- | --- |
| Docker and OS services | Generated apps run in a browser-side Node.js runtime, not a Linux Docker daemon. bolt.diy is explicitly focused on Node.js apps.[^bolt-readme] | It cannot replace Horizon's Docker environment for arbitrary services, Docker Compose, system packages, or production-parity validation. |
| Native dependencies | Official docs say WebContainers execute web-native languages (JavaScript and WebAssembly); native Node addons such as C++ addons cannot load unless replaced/compiled to WASM.[^wc-native] | Packages using native binaries need compatibility checks or must fall back to Docker. |
| Databases | bolt.diy's Supabase integration calls the external Supabase management API over HTTP; it does not start Postgres inside the preview runtime. Evidence: [`app/routes/api.supabase.query.ts#L17-L28`](https://github.com/stackblitz-labs/bolt.diy/blob/2e254ac19a696394030601bc602f54945b12bfc4/app/routes/api.supabase.query.ts#L17-L28). | Browser-compatible remote DB APIs or WASM databases can support drafts, but migrations and production DB access should remain server-governed. |
| Secrets | The runtime and its filesystem are controlled by the end user's browser. In this revision, bolt.diy also persists its Supabase connection/token/credentials in localStorage: [`app/lib/stores/supabase.ts#L54-L83`](https://github.com/stackblitz-labs/bolt.diy/blob/2e254ac19a696394030601bc602f54945b12bfc4/app/lib/stores/supabase.ts#L54-L83) and [`#L126-L143`](https://github.com/stackblitz-labs/bolt.diy/blob/2e254ac19a696394030601bc602f54945b12bfc4/app/lib/stores/supabase.ts#L126-L143). | Never inject LiteLLM master/virtual keys, tenant DB credentials, S3 secrets, or publish credentials into a WebContainer. Proxy privileged operations through Horizon APIs with auth, quota, guardrails, and audit. |
| Browser/platform | WebContainers require `SharedArrayBuffer`, cross-origin isolation, COOP/COEP, HTTPS in production, and compatible iframe headers. Full support is strongest on Chromium. Official docs flag Brave's aggressive third-party blocking and reduced Firefox/Safari support.[^wc-browser][^wc-headers] | Add capability detection and a Docker-only fallback. Brave Shields/cookie configuration will create support cases if browser preview is mandatory. |
| Capacity/lifecycle | The official API allows one WebContainer instance per page, although it can expose multiple ports. Several projects/tabs can exhaust browser WASM memory.[^wc-quickstart][^wc-native] | Treat it as one active local draft workspace, not a server scheduler. Evict/snapshot on project switch and keep durable source on Horizon. |
| Collaboration | Files and live processes are local to one user's browser. | Real-time team editing, background jobs, scheduled tasks, and app-user access still need server-side state/runtime. |
| Licensing | Official docs require a commercial WebContainer API license for production, for-profit customer or employee use; POCs do not require one.[^wc-license] | Horizon must confirm commercial terms and use a supported public/enterprise SDK. bolt.diy pins an internal build, `@webcontainer/api@1.6.1-internal.1`, which Horizon should not copy.[^bolt-package] |

## Comparison with Horizon's current Docker path

Existing local Horizon measurements are:

| Stage | Horizon observed time | bolt.diy equivalent |
| --- | ---: | --- |
| Project creation to first chat | 21.4–23.2 s | No server project-container provisioning before the browser runtime can boot |
| Pre-container resources | about 15.7 s | External DB/object storage/LLM provisioning is not in the preview boot path |
| Container create + health | 5.5–7.5 s | Replaced by WebContainer boot and browser event-driven `server-ready` |
| Next.js startup | about 1.1 s | Still exists; Vite/Next/server startup runs inside the WebContainer |
| Fresh project volume | about 660 MB, mostly `node_modules` | Browser virtual filesystem plus installed dependencies; no Docker named-volume copy-up |
| Warm stopped container to ready | about 1.73 s | New/reloaded tab restores source then may need dependency install/start again |

The measurements come from Horizon's existing [`dev-workspace-container-startup.md`](./dev-workspace-container-startup.md). They are not a direct benchmark of bolt.diy. StackBlitz's official “milliseconds” claim describes spinning up the WebContainer development environment, not the entire generated-app path including network package installation and framework compilation.[^wc-intro]

## Recommendation for Horizon

### Adopt the preview pattern, not bolt.diy's trust model

1. **Instant draft lane:** boot one WebContainer when Creator opens a project and mount a small, prebuilt browser-compatible starter snapshot. Let Pi stream safe source edits into it and start Vite immediately.
2. **Authoritative lane in parallel:** provision/wake the existing per-project Docker workspace concurrently. Keep all Horizon custom tools, repository checkpoints, secrets, database migrations, validation, publishing, and app-user runtime there.
3. **Clear handoff:** label browser output “Draft preview.” Switch to “Workspace preview” once Docker is ready. If the project requires native modules, server-side secrets, unsupported packages, or non-Node services, skip the draft lane automatically.
4. **Keep server persistence:** mirror every accepted source patch to the Horizon project repository/API. Use IndexedDB only as a local recovery cache, never as the authoritative project store.
5. **Use bulk hydration:** create a WebContainer-compatible golden snapshot and use `mount(snapshot)` rather than thousands of sequential writes on initial load. Only stream incremental edits afterward.
6. **Protect credentials:** Pi and LiteLLM remain in `platform-api`; browser preview gets short-lived, narrowly scoped Horizon API tokens only when necessary. Never expose infrastructure credentials or rely on client-side guardrails.
7. **Measure before committing:** benchmark browser boot, snapshot mount, cached/fresh install, first server-ready, first paint, memory, Brave/Chrome compatibility, and fallback rate on the Horizon starter. Also validate Next.js compatibility; Vite is the easier first target.

If Horizon wants one production runtime with exact database/native-tool parity, WebContainers are not a replacement. In that case, continue the source-only `volume-nocopy` and parallel provisioning work documented in the existing startup report. If the goal is perceived creator speed, the hybrid gives an immediate UI preview without sacrificing Horizon's governed backend boundary.
